"Anywhere you find an either/or, look for the common structure, recursively" applies at BUILD/COMMIT time, not just at design time. The failure mode the user caught (and watched "thrash commit by commit"): facing "n=3 special case OR n-generic," I built the n=3 rung (TrilinearUniversal, commit d0510ee) and THEN the generic that subsumes it (multilinear-extensionality, the very next commit) — committing BOTH sides. The special rung ended up imported by 0 = dead thrash.

**Why:** building the special case "first, as a safe brick" feels prudent but produces redundant artifacts the moment the general lands; each parallel rung is a separate commit, so the redundancy reads as thrash accreting commit-by-commit. The either/or {special, general} has an obvious common structure (the generator); the disciplined move is to build the generator ONLY, and derive/instantiate the special cases from it (or omit them if they have no consumer).

**How to apply:**
- When you catch yourself about to build a special case "on the way to" the general, STOP — build the general; the special case is an instance.
- A representation either/or (bundled record vs uncurried predicate, curried vs uncurried) is ALSO an either/or: keep the ergonomic one consumers need, but BRIDGE it to the generic via a thin adapter — don't write a parallel proof. ("bilinear IS multilinear-extensionality at arity 2" via a `Bilinear → IsMultilinear` adapter.)
- Before committing a new rung, grep its importers; imported-by-0 right after a more-general commit = thrash, collapse it.
- Asserting "they run the same recipe" in a comment WITHOUT a derivation is a mini-overclaim ([[discipline/feedback_spec_is_proposal_not_claim]]); build the bridge so the shared structure is proved, not claimed.
- Sibling of [[feedback_grow_to_maturity_not_approximate]] (don't approximate then rebuild) and [[feedback_agreement_without_yielding]] (actually collapse, don't just say "you're right" and rebuild parallel rungs next turn).

**The keep/delete reflex IS the LEM trap (user caught this, hard, 2026-06-18 on the Stab-normality cluster).** When I "audit for redundancy" by asking pairwise "is X redundant with Y? keep or delete," that binary classification is itself excluded-middle — and it THROWS AWAY the structure-finding (declaring prior attempts "redundant"). Don't classify; find the GENERATOR and make the others its readings. Concretely:
- **A `¬P` is never a peer fact to "keep" beside a positive characterisation — it is the NEGATIVE POLE of that structure, and must be GENERATED by it.** I had `StabD-not-normal` (a ¬) and the iff `member-normal ⟺ stab-fixes-orbit`, and said "not redundant, keep both" — diving into LEM. Fix: the ¬ = the iff's ⟹ direction read at a CONCRETE failure witness ([[feedback_reject_lem_in_substrate]]). Likewise the positive pole (fixed⟹normal) = the iff's ⟸ direction at the trivial case. ONE structure (how Stab varies over the orbit); two poles, both generated; both iff directions consumed.
- The deepest root (e.g. `Stab-conj-equivariant`, the orbit map) is NOT pruned as "redundant" — it's a distinct positive fact / facet. Pruning prior structure-finding as redundant is the same error inverted.
- Agda note that fell out of the honest collapse: a predicate hiding `{g n}` behind a `Foo X = {g n} → …` abbreviation CANNOT have those implicits instantiated at concrete witnesses downstream (`apply`-projection inference blocks it). Make ∀-quantified obligation/characterisation predicates EXPLICIT in their quantifiers so they compose.
